IT DOES NOT. This NAME-FREE AND COUNT-FREE replacement for the whole
non-challenge branch compiles EXIT 0, and deleting its first line is REJECTED
("invalid last instruction"), so it is load-bearing rather than a no-op:

    do ? (rcondf{1} ^if; first by auto => /#).
    wp; call (_: true).      (* x8 -- one per call, both sides aligned *)
    ...
    wp; skip => /#.

Three facts make it work, and each was measured:
 * `rcondf{i} ^if` works with an ABSTRACT CALL still in the prefix. The second
   dead guard is the literal `false`, so the hoare-side obligation is trivial and
   `auto` never has to step over the call. That is what removes the need to peel
   the challenger's `decaps` first, which is what forced the numeric `seq 2 1`.
 * with both guards gone the two branches hold the SAME EIGHT CALLS IN THE SAME
   ORDER, so a plain backward ladder covers them all -- including the two
   `decaps` -- and no intermediate result ever has to be NAMED. That is what
   removes `_r00`/`_r10`/`ct0`, the EC-inline-renamed names.
 * `do ?` makes the number of dead guards structural instead of counted, so the
   flat state's disagreement about how many `if`s there are stops mattering.

So the route can be driven off the FLAT STATES, like
`_synth_correctness_decaps_casesplit`, and needs no `oracle_tac_override`. The
remaining hop-specific data are all flat-state readable: the shared-prefix length,
the one-sided `encodesharedsecret` and its `_det` axiom, the field holding its
argument, and the regroup lemma name (`types.probe_concat_regroup`).

Note the emitted coupling writes `RD.pq_keys{2}.`2` where the tactic above writes
`RD.pq_keys.`2{2}`; both are valid EC and mean the same thing.

*** THE MIRROR HOP (`hop_10_decaps`) IS A SEPARATE, MEASURED SUB-WALL. ***

`hop_5` and `hop_10` are mirror images -- at `hop_10` the KDF-PRF challenger sits
on the LEFT (`RE`, using `challenger_k` directly, key-prepended) and the KEM
challenger on the RIGHT (`RC`, ENCODING `ss_PQ` and left-nesting) -- so the
`decaps` route's shape gate is satisfied there too. But `hop_10`'s COUPLING

WHY, read off the two flat states' `initialize` backbones. At `hop_5` the
challenge KDF output is still computed in `initialize`, so the encoding call is
present there and `_synth_kdf_key_substitution` can pair the two draws through
it. By `hop_10` that output has been replaced by a fresh random `ss` (hops 6-9),
so `initialize` no longer contains the encoding -- it contains only two
one-sided draws of the SAME distribution:

    Step_10L_state_0.initialize:  challenger_k                  <$ dbs_kem_pq_nss
    Step_10R_state_0.initialize:  challenger_Initialize_ssStar0 <$ dbs_kem_pq_nss

`_bd_events` tags a sample by its bound VARIABLE, so those two never match, and
`_synth_bundled_delegate_reorder` aligns the backbones by DROPPING each one-sided
(`swap{1} [7..10] -4` then `rnd{2}` ... `rnd{1}` ... `smt(dbs_kem_pq_nss_ll)`).
That is sound -- the hop's post never mentions either variable -- and it is why
`hop_10_initialize` is green today. It is also exactly what destroys the
information `hop_10_decaps` needs: the drop throws away the only chance to couple
the two draws.

SO THE MIRROR NEEDS AN ESTABLISHING-SIDE BUILD FIRST, not a consumer tweak.
Shape of the route (`_synth_dead_key_bijection_init`, not yet written):

   where one side applies a `deterministic injective` single-argument method to
